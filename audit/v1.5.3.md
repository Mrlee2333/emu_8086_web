## Read the deltas, not the absolutes

**The absolute timings in this report are not comparable to the ones in
`audit/v1.5.1.md` or `audit/v1.5.2.md`, and must not be.** `v1.5.1` measured a
131,072-step loop at 5.93 ms and `v1.5.2` at 10.35 ms; the same loop on
essentially the same code measures 13.0–17.0 ms here. The cause is the machine,
not the branch: a QEMU virtual machine was at 375 % CPU for this session and the
load average sat between 12 and 14, with `StorageManagement` and `WindowServer`
also busy. Every number below was therefore taken as an **interleaved pair** —
baseline, then this branch, then baseline, then this branch — so that whatever
the competing processes did, they did to both sides.

Three successive audits have now hit this on the same machine, and the
conclusion is worth stating once: **on a busy host these timings cannot
distinguish a 1 % regression from a scheduling artefact, and any report that
quotes a bare delta without the load it was taken under is not evidence.** What
makes these numbers usable is not their precision but the structural claim,
which is checkable without a timer at all — see *vs v1.5.2* below.

Both median and minimum are reported because they answer different questions
under load. The minimum is the best run achievable on a quiet moment, so it is
the closest thing to the "real" figure; the median is what a user would
ordinarily see. When the two disagree, the disagreement is the noise.

## vs v1.5.2

- **The emulator is untouched, and this time that is provable without a timer.**
  `git diff --name-only <base> HEAD` over `lib/emulator`, `lib/ide/memory-search`
  and `electron/` returns **nothing**. The benchmark is not needed to establish
  that the step loop, the assembler, memory search and the desktop shell cannot
  have changed; the benchmark is only there to confirm the file list is not
  lying. It does, and the figures are flat: step loop −0.7 % on median and
  +3.2 % on minimum, print loop −1.9 % and −0.7 %, snapshot +9.7 % and −5.1 %.
  Every one of those sign-flips or stays under 2 % between the two estimators,
  which is what noise looks like under load 12–14. Search is quoted on the
  median only: at 0.066 ms a single scheduling quantum is several percent of
  the measurement, so its 0.0287 ms minimum is an artefact of one lucky pair,
  not a result.
- **The bundle grew 6,210 B, and the `/` route is now at 97.8 % of budget — the
  tightest it has ever been.** This is the fourth release in a row to land on
  `/`, and the rebase is what pushed it: my feature's own cost is unchanged at
  6,210 B, but v1.5.2 added its own weight, so the route went 96.2 % → 96.9 % →
  **97.8 %**. **15,988 B of headroom remain**, which is one small feature or
  three bug fixes. The button the whole viewer hangs off is a static import on
  the IDE path, so every visitor pays for it whether or not they ever open it.
  The honest move before the next feature lands here is a dynamic import for
  dialog-only components — the pattern `qrcode` already uses for `/`, which is
  what took that route from 743,962 B to 667,307 B in v1.3.2 — or an honest
  raise of the ceiling with the headroom argued on the record, not another 5 KB
  of creeping additions. Two audits have now flagged this and this is the second
  release to act on neither, so it should be treated as owed, not noted.
- **The measure that matters for this change is not in the table above.** A
  register display is either right or quietly wrong, and a benchmark cannot see
  that. The 19 tests in `lib/ide/value-view.test.ts` check the two things a
  viewer can get wrong: the byte split, against `Machine.get8` on real machine
  state after `MUL` (both widths), `XLAT`, and a `MOV AH,1` that leaves AL
  alone; and the character row, against what `dosByteToPrintable` would draw
  for the same byte across 0x80h–0xFEh, so the viewer cannot drift away from
  the console printed two inches above it.
- **The one place this feature could have taught something false is the
  character row, and it is where the work went.** The original emu8086 viewer
  labels that row ASCII. A byte above 7Fh is not ASCII: read as Latin-1, 0xA3h
  is a control code, and a student comparing the viewer with the console
  directly above it would see a glyph there and nothing here. The row therefore
  reads CP437 — the same table the console and the character map use — and
  says so in a note, so the app does not quietly disagree with the original
  while being right about the hardware. Two of the tests written for this
  asserted the *wrong* thing and were corrected against the emulator rather than
  the other way round: byte `MUL` overwrites AL with the remainder, so 200 × 3
  leaves AL = 88, not 200; and 0x0D00 puts 0Dh in AH, not in AL.
- **No memory bound moved, and nothing new is retained across a run.** Two
  `useState` values exist while the viewer is open — which register the panel
  opened it on, and which register the picker has moved to — and neither
  outlives the dialog, which is unmounted when closed. A closed viewer costs
  nothing but the `string` the panel holds to remember it is shut. The picker
  reads the `RegView[]` the panel already builds each render — the viewer
  derives from those descriptors instead of re-splitting the word, which is why
  it cannot disagree with the Details table sitting one click away.

## The rebase

Twice, for two different reasons, and the second is the one that matters.

**First: v1.5.1 → v1.5.2**, because v1.5.2 had by then been rebased onto the
reviewed v1.5.1 and became the real previous version. It is worth recording what
that cost and what it caught.

**Four conflicts, all mechanical.** `lib/version.ts` and `package.json` (two
versions claiming one field), `lib/changelog.ts` and `CHANGELOG.md` (both
adding a section at the top). Each was resolved by keeping both entries in
version order, newest first — 1.5.3, then 1.5.2, then 1.5.1 — rather than by
picking a side. The `CHANGELOG.md` resolution also gained a note recording that
this branch now sits on 1.5.2, so a reader arriving from `main` later is not
left guessing why the section above it is a version this branch never touched.

**The conflict that mattered was the one that did not happen.**
`components/ide/cpu-panels.tsx` — the only file this feature edits that the base
also edits — **auto-merged with no conflict at all**, and that is exactly the
case worth distrusting. v1.5.1's second review had restructured the same
function: it now derives the panel's cell order from the exported
`GENERAL_ORDER` and `SEGMENT_ORDER` instead of literals, and the Details footer
prints the `REP` prefix off `curInstr.rep`. A silent merge in that file could
plausibly have kept my two buttons and dropped a prefix, or vice versa, with a
green build and no warning.

So it was checked by construction rather than by eye: `git diff <base> HEAD --
components/ide/cpu-panels.tsx` was read line by line to confirm the diff
contains **only** the two entry points and nothing else. It does — 78 changed
lines, every one of them the `ValueViewer` import, the `onInspect` prop, the
`viewing` state, the `inspect` helper, the header button and the render. Then
the same was done for the whole branch: 9 files, of which 4 are new and 5 are
mine to edit, and no base file is left holding a partial version of my work.

**Verified live afterwards, not assumed.** Both entry points reopened on the new
base, the panel header button reproducing the reference screen exactly
(`0xA341` → `A3`/`41`, `243`/`101`, `163`/`65`, `-93`/`65`, `41793`, `-23743`)
and a Details row opening on the register that row names. Escape still closes
one dialog and not the layer under it. And the feature that v1.5.1's second
review added was exercised *in the same dialog* as this one, because that is
where a markup change like mine would collide: a `REP MOVSB` step shows
`Next: REP MOVSB — runs the whole instruction CX times, stepping SI or DI each
time and counting CX down to zero`, and the per-row `i` in that same dialog
still opens the viewer on `SI`. The two features coexist.

**What the rebase did not change, and this is the point.** `RegView` and
`RegByteView` are untouched by v1.5.1's second review — it changed the purpose
sentences, exported two order lists and added `prefixedInstructionNote`, all of
which sit beside the types rather than inside them. So
`lib/ide/value-view.ts`, which copies the halves out of a `RegView` instead of
re-splitting the word, needed no change and all 19 of its tests passed
unmodified. That is the payoff of deriving from the descriptor rather than
from the raw register: the one dependency this feature has on v1.5.1's data
shapes turned out to be a stable one.

**Second: v1.5.2 → `main`**, once #14 and #15 merged and the automation had
tagged and published v1.5.1 and v1.5.2. This one was cheap, and the cheapness
is the finding: `git rebase origin/main` reported five commits skipped as
previously applied, because the v1.5.2 work reached `main` through two merge
commits rather than as a linear chain, and the content was already present. The
only thing `main` carried that the old linear tip did not was a reword of the
`ax` purpose sentence in `lib/ide/reg-info.ts` plus 14 lines of test and audit
prose.

That reword is worth a second look, because `ax` is the register the viewer's
picker opens on. It changed `PURPOSE.ax` and nothing else — `RegView` and
`RegByteView` are still untouched, which is now the third release in a row to
leave those types alone while editing the module around them. The viewer derives
every number it shows from the `RegView` the Details view already renders, so a
sentence edit cannot reach it. Confirmed live: the panel's own `i` shows the new
wording, and the viewer is unaffected.

Re-verified after the rebase rather than assumed: both entry points, the
reference screen exactly, the two-column form for a register with no halves,
Escape closing one dialog and not the layer under it, the `Char` cell still on
`text-ink`, and `APP_VERSION` reading 1.5.3 in the toolbar. 496 pass / 0 fail.

## Re-review findings (v1.5.3, second pass)

A second pass over the finished branch, before merge. It found five things, all
in the display layer and none in the derivation.

1. **The release notes and the dialog subtitle claimed something the code does
   not do — in six places.** The subtitle read "One value in every base", and
   `lib/ide/value-view.ts`, `CHANGELOG.md` and `lib/changelog.ts` all said the
   *word* is shown in hex, binary and octal. It is not: octal is shown for the
   two bytes, and the word is shown as hex, binary and decimal. The original
   groups the 16-bit rows under "Decimal 16 bit" for exactly that reason. The
   claim was wrong in the one direction that matters, because it promised a
   reading the reader would go looking for. All six now say what is on screen,
   and say why octal stops at the byte.
2. **The `Char` row was painted in the app's accent colour.** `text-amber` is
   this app's colour for something you can act on — buttons, the dialog title,
   the "Next:" note. A character is data, not an action, so the row was
   borrowing a meaning it does not have. Measured, it was also the
   lowest-contrast cell in the table: **4.25:1** in the light theme, against
   4.35:1 for `text-green` and 4.97:1 for `text-ink`. Both mistakes were the
   same mistake, and dropping the row to `text-ink` removed a `tone` from the
   union as well as the lowest contrast figure — the Char cells now measure
   4.97:1.
3. **A doc comment described a case that cannot exist.** `ValueByte.name` was
   documented as "or 'H' / 'L' for a register the 8086 gives no name to".
   `reg-info.ts` sets both halves or neither, and only for AX, BX, CX and DX,
   which always have real names. A maintainer would have gone looking for
   half-name handling that was never written.
4. **A second, independent spelling of the column count.** `ByteGroup` hardcoded
   `cols={3}` on its caption. Correct at its only call site, which sits inside
   the `high && low` branch where three is what `cols` already is — but it was
   a constant agreeing with a variable by luck. `cols` is now passed down.
5. **An undocumented invariant holding the dialog together.** `useState(initial)`
   reads `initial` once, which is only right because the panel mounts the viewer
   only while it is open. Nothing enforced that, and nothing says so; a future
   keyboard shortcut that could reach the dialog while it was open would make
   the picker silently disagree with the prop. The comment now says so and names
   the `key` that such a path would need.

Two things the re-review checked and found sound, and are worth recording
because they are the ones most likely to be wrong:

- **The viewer does not lag the CPU by a step.** Stepping a `add ax, 0A341h`
  loop eight times with the dialog open, the viewer's 16-bit unsigned reading
  agreed with the panel's hex on **every** step including the `loop`
  back-edge, and the picker kept its selection throughout. It also agreed after
  a `Run`. The obvious hazard was real — `machine` mutates in place, so a
  `useMemo` on it would have gone stale — but the viewer recomputes from the
  `RegView[]` the panel builds each render, so it is not exposed.
- **390 px and the light theme.** The dialog fits at 390 px wide with no
  horizontal overflow, and every text node in it was measured against its
  effective background in both themes.

### Contrast, and what was deliberately left alone

Sweeping every text node in the dialog against its resolved background leaves
four cells under the 4.5:1 that WCAG AA wants for 12–14 px text, in the light
theme only: the dialog title at 4.25:1 (that is `DialogShell`'s own
`text-amber`, shared by every dialog in the app) and the three hex cells at
4.35:1 (that is `text-green`, the token the compact register panel and the
Details table already use for every hex value on screen).

**Neither was fixed here, on purpose.** Both are app-wide design tokens, and
darkening them would change every register value, every memory-dump address and
every dialog title in the product. That is a design change for its own PR, with
its own review, not something to slip into a feature branch. The `Char` row was
different: that colour was this feature's own choice, so it was this feature's
own to give back.

## Reproduce

```sh
bun run verify                    # lint, typecheck, tests, build, budget

# The baseline needs a real install. Turbopack rejects a node_modules symlink
# pointing out of the filesystem root, so `bun run build` in the worktree below
# fails with TurbopackInternalError until this is done. audit/bench.mjs never
# starts Next and tolerates the symlink, but the bundle figures above came from
# a real build, so use a real install for both.
git worktree add --detach /tmp/emu-base-152 feature/mac-desktop-fixes-v1.5.2
(cd /tmp/emu-base-152 && bun install && bun run build && bun run bundle:budget)

bun audit/bench.mjs               # this version
(cd /tmp/emu-base-152 && bun audit/bench.mjs)
# interleave the two, 12 pairs for steps/print/search and 7 for snapshot.
# do NOT compare one run to another: at load average 12+ the run-to-run band is
# wider than any effect this change could have had, which is why the pairs and
# the file-level diff are both recorded above.
```

The structural check is the one that does not need a quiet machine, and it is
the one to run first:

```sh
git diff --name-only feature/mac-desktop-fixes-v1.5.2 HEAD \
  | grep -E 'lib/emulator|lib/ide/memory-search|electron/'   # must print nothing
```
