# Audit — v1.5.3

- Branch: `feature/extended-value-viewer-v1.5.3`
- Base: `feature/register-details-v1.5.1` (4f94f05) — the Extended Value Viewer
  extends the v1.5.1 register Details view, and that view is the only place on
  screen where all thirteen registers are named at once
- Date: 2026-09-28
- Machine: Mac arm64 (Apple M4) · macOS 27.0 · `bun 1.4.2`
- Benchmark: `bun audit/bench.mjs` (the frozen workload from `audit/README.md`,
  unchanged since v1.3.2), run **interleaved** with a `git worktree` at the
  v1.5.1 tip — 14 alternating pairs for the step/print/search figures, 7 pairs
  for the snapshot figure
- Scope: emulator step loop, step-back snapshot cost, console output cost,
  memory search, first-load bundle, and the memory bounds

## Read the deltas, not the absolutes

**The absolute timings in this report are not comparable to the ones in
`audit/v1.5.1.md`, and must not be.** That report measured a 131,072-step loop
at 5.93 ms; the same loop on the same code measured 13.4–18.3 ms here, roughly
2.5× slower. The cause is the machine, not the branch: `CleanMyMac` was at 207 %
CPU and the load average sat between 10 and 13 for the whole session, with
`trustd`, `StorageManagement` and `WindowServer` all busy. Every number below
was therefore taken as an **interleaved pair** — baseline, then this branch, then
baseline, then this branch, 14 times — so that whatever the competing processes
did, they did to both sides.

Both median and minimum are reported because they answer different questions
under load. The minimum is the best run achievable on a quiet moment, so it is
the closest thing to the "real" figure; the median is what a user would
ordinarily see. When the two disagree, the disagreement is the noise.

## vs v1.5.1

- **The emulator is untouched, and the benchmark confirms it.** No file under
  `lib/emulator/` changed, and none of `memory-search.ts`, `machine.ts` or
  `assemble.ts` was touched from outside it either. The step-loop, snapshot,
  print-loop and search figures move by −4 % to +1 % with the sign flipping
  between the median and the minimum, which is what noise looks like; the two
  metrics that came out *faster* on median (snapshot −4.2 %, console text
  −14.0 %) are faster because the load dipped during those pairs, not because
  anything got quicker. Search is quoted on the median only: at 0.065 ms a
  single scheduling quantum is several percent of the measurement, so its
  minimum (0.0295 ms) is an artefact of one lucky pair, not a result.
- **The bundle grew 6,024 B, and the `/` route is now at 97.1 % of budget.**
  That is 4,571 B for the dialog and its state, and the remaining ~1,450 B for
  `lib/ide/value-view.ts`. The whole feature is reachable from a button, so it
  is statically imported on the IDE path and is paid for by every visitor. This
  is the third release in a row to land on `/` and it is the tightest that
  route has been: **20,986 B of headroom remain**, and the next feature to add
  UI here will not fit. The honest move before that one lands is either a
  dynamic import for dialog-only components (the pattern `qrcode` already uses
  for `/`, which is what took that route from 743,962 B to 667,307 B in v1.3.2)
  or an honest raise of the ceiling, not another 5 KB.
- **The measure that matters for this change is not in the table above.** A
  register display is either right or quietly wrong, and a benchmark cannot see
  that. The 19 tests in `lib/ide/value-view.test.ts` check the two things a
  viewer can get wrong: the byte split, against `Machine.get8` on real machine
  state after `MUL` (both widths), `XLAT`, and a `MOV AH,1` that leaves AL
  alone; and the character row, against what `dosByteToPrintable` would draw
  for the same byte across 0x80h–0xFEh, so the viewer cannot drift away from
  the console printed two inches above it.
- **The one place this feature could have taught something false is the
  character row, and it is where the work went.** The original emu8086 viewer
  labels that row ASCII. A byte above 7Fh is not ASCII: read as Latin-1, 0xA3h
  is a control code, and a student comparing the viewer with the console
  directly above it would see a glyph there and nothing here. The row therefore
  reads CP437 — the same table the console and the character map use — and
  says so in a note, so the app does not quietly disagree with the original
  while being right about the hardware. Two of the tests written for this
  asserted the *wrong* thing and were corrected against the emulator rather than
  the other way round: byte `MUL` overwrites AL with the remainder, so 200 × 3
  leaves AL = 88, not 200; and 0x0D00 puts 0Dh in AH, not in AL.
- **No memory bound moved, and nothing new is retained across a run.** The
  picker's selected register is one `useState` string, and the dialog is
  unmounted when closed, so a closed viewer costs one `string`. The `Watch`
  dropdown reads the `RegView[]` the panel already builds each render — the
  viewer derives from those descriptors instead of re-splitting the word, which
  is why it cannot disagree with the Details table sitting one click away.

## What changed, and what it cost

| Change | Cost |
|---|---|
| `lib/ide/value-view.ts` | Pure. Builds a descriptor from a `RegView`; no Machine, no React, no allocation retained |
| `components/ide/value-viewer.tsx` | Mounted only while open; one `<select>` and one table |
| `RegisterPanel` state | One `useState<string \| null>` for the open dialog, one more for the selected register inside it |
| Per-row `i` in the Details table | One button per register row, rendered only while that dialog is open |

## Reproduce

```sh
bun run verify                                     # lint, typecheck, tests, build, budget
bun audit/bench.mjs                                # this version
git worktree add --detach /tmp/emu-base-151 feature/register-details-v1.5.1
ln -s "$PWD/node_modules" /tmp/emu-base-151/node_modules
bun /tmp/emu-base-151/audit/bench.mjs              # the previous version
# interleave the two, 14 pairs; do not compare one to the other directly
bun test lib electron
```

Note: the baseline worktree only needs a real `bun install` to run
`bun run build` — Turbopack rejects a `node_modules` symlink pointing out of
the filesystem root, which is why `audit/v1.5.1.md` says so. `audit/bench.mjs`
never starts Next, so the symlink is enough for the benchmark, and that is
what the paired runs above used. The machine must be quiet: at load average 10+
the run-to-run band is ±25 %, which is wider than any effect this change could
have had.
