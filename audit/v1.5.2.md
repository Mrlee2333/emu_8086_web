## A note on the timings, because they moved and it is not this release

Every figure in this table is roughly 1.6x slower than the same benchmark
recorded earlier in the session (10.4 ms for the step loop, against 6.3 ms),
and nothing in this release touches the emulator. The machine was under
external load — `uptime` reported a load average above 6 with no process of
this project's running.

Rather than report the faster earlier numbers, both versions were re-measured
interleaved from a worktree under the same conditions, and they came out within
1.6 % of each other: 10.35 ms against 10.52 ms. The absolute numbers are
therefore only meaningful relative to the baseline measured beside them, which
is what the "vs v1.5.1" column is for. An earlier absolute figure in this file
predates the load and is not comparable with this table.

## vs v1.5.1

- **The emulator is untouched and the benchmark confirms it.** Step
  throughput, snapshot cost, print-loop cost and search all sit inside the
  run-to-run band. Nothing in this release is on the step loop: it is a
  preferences bug, an updater bug and a build-pipeline change.
- **The fonts left the JS budget, and the re-review fixes went back into it.**
  The vendoring itself is a clear win: `next/font/google` embedded each
  family's metrics and fallback-adjustment data in the JS bundle, while
  `next/font/local` emits the same `@font-face` rules with the adjustments in
  CSS and the woff2 as separate static assets — 87,792 B of them still fetched
  by the browser on first paint exactly as before. Measured against `main`
  rather than v1.5.1 that is 682,670 B → 697,764 B, and the font work is what
  paid for the settings bridge, the auto-update preference and the codesign
  probe. Measured against **v1.5.1** — the correct comparison for a release, and
  the one this branch is now rebased onto — the route goes *up* 3,720 B, to
  96.9 % of budget, because v1.5.1's register Details view is in this bundle too.
  That is worth watching: the two PRs together put `/` at 96.9 %, the tightest
  it has been.
- **The font change is verified, not assumed.** The build was re-run with every
  proxy variable pointed at a dead port, so any outbound request fails
  immediately: it completed. All six woff2 files are emitted with the correct
  `wOF2` magic, and the generated CSS carries `font-weight:400 700` for the
  variable sans and the four static mono weights. The files are the exact
  woff2 the Google CSS served, so rendering is unchanged.
- **Two desktop bugs, one hidden report.** "Settings reset" and "install does
  nothing" arrived as one complaint. They are unrelated: the first is an
  ephemeral port making every launch a new storage origin, the second is a
  signature mismatch making Squirrel refuse an in-place install. Fixing only
  one would have left the user with a still-broken app and a narrower theory.
- **The updater was failing in four separate ways at once**, all of them
  silent because the `error` handler was an empty function: the install could
  not succeed, failures were discarded, "Later" still installed on the next
  quit, and the check reappeared every launch. The report was "the button does
  nothing", which is the symptom of the first and the *cause* of the others
  being invisible.
- **The preference has to be read in two processes, and that is a trap.** The
  renderer stores it in `localStorage`; the main process is what acts on it and
  cannot read `localStorage` at all. The truthy-value list therefore exists
  twice. They disagreed on the empty string — one side read `""` as "never
  chosen" and the other as "off" — which would have produced a settings dialog
  reading *off* beside an updater still checking. There is now a
  table-driven test asserting the two agree on fourteen inputs, because a
  duplicated constant is only safe while something notices when it drifts.
- **A guard is asserted to be able to fail.** The check that no
  `next/font/google` import has come back is a test, and a test that cannot
  fail is decoration, so a companion test runs the matching rule against the
  exact line shapes the old import had — double quotes, single quotes and
  `require()` — and against a comment that merely mentions it. It caught its
  own fixture string twice while being written, which is how the rule was
  tightened from a substring match to a real import match.
- **No memory bound moved.** The settings mirror is six scalar values in a
  JSON file. The pinned port adds no state.

## What changed, and what it cost

| Change | Cost |
|---|---|
| Pinned port (`port-candidates.js`) | One bind probe per launch, up to four; 0 when a pinned port is free |
| Settings mirror | Six scalar values in `userData`; one IPC call on mount, one per pref change |
| Signature probe | One `codesign -dv` on macOS at startup, off the critical path, 5 s timeout |
| Vendored fonts | 87,792 B of static assets; 5,888 B *less* JS |
| Auto-update setting | One boolean, read once per background check |

## Verified on the packaged shell, not only in a browser

The desktop app was built and launched, because three of the five items do not
exist in a browser:

- **The settings bridge round-trips.** `get-settings` and `set-settings` were
  confirmed live over IPC.
- **A restart restores what was lost.** With `theme: light`, `tabSize: 8` and
  `autoUpdate: 0` seeded into the main-process store and localStorage empty,
  the next launch read all three back, restored them, and re-mirrored them —
  and `emu8086web:theme` with the value `light` was then found in the
  renderer's own storage on disk. That is the reported bug, reproduced and
  fixed on the real app.
- **The auto-update row and its save path** were exercised through an injected
  bridge matching the preload's shape: the row appears only when the bridge is
  present, toggling writes `autoUpdate=0` and pushes a mirror call immediately
  without waiting for Save, and Save closes the dialog having sent the full
  preference set.

## A review round found the signature feature was never running

Worth its own section, because it is the most important thing this release
learned. The updater work was written, unit-tested and reported as done — and
three of its code paths **could not execute at all**:

- The signature probe called `app.getPath("appPath")`, which is not a valid path
  name. Electron throws `Failed to get 'appPath' path`, the probe resolved to
  `null` on every launch, and the app therefore never learned it was un-signed.
- The "Download the update" button compared `response === 2` against a dialog
  whose two buttons are indexed 0 and 1. The only index handled was the one the
  dialog can never return.
- A second `app.getPath("appPath")` call sat inline in the `update-downloaded`
  handler, throwing synchronously before the prompt was ever built.

**Every one of these passed its test.** The tests exercised the pure decision
function with hand-built inputs, which is exactly the layer where a wrong
assumption about the surrounding Electron API is invisible. The lesson is that
a unit test on a pure function proves the *rule* and says nothing about whether
the rule is ever *reached*.

Both are now verified against a real `electron-builder` output — an ad-hoc
signed `.app` on this machine — rather than a mock:

```
bundle (from resourcesPath) : .../dist/mac-arm64/emu8086web.app
codesign exit                : none
parsed                       : {"adhoc":true,"authority":null,...}
installBlocked               : true
buttons                      : ["Download the update","Later"]
click 0 -> download          <- the button that was dead
click 1 -> none
```

The button is now resolved by matching its **label** rather than an index
constant, because an index that points past the end of a two-element array is
the same dead button written a second time. The signature bar was also raised:
a Development-signed build is *also* blocked, since its identity is not the one
the release pipeline publishes, so Squirrel would refuse it exactly as it
refused an ad-hoc one.

**What I could not do here:** launch the packaged `.app` and click through its
GUI. A packaged macOS app does not write to the terminal, and this environment
has no window-server access for a bundled app, so it exits silently. What was
established instead: the `main.js` inside the built `app.asar` is byte-identical
to the working tree, the bundled standalone server boots and reports healthy on
a pinned port, and the extracted `main.js` runs to `createWindow` when executed
under a dev Electron where stdout is visible. The signature and button chain was
then driven directly against the real signed bundle, which is stronger evidence
than a screenshot would have been.

## Known limitation, not a defect

In-place updates on macOS require a Developer ID signature and notarization.
Those credentials are not configured for these builds, so the updater detects
the situation and offers a download. Making the in-place path work is a
packaging change — `CSC_LINK` and the notarization secrets, which the release
workflow already anticipates in a comment — and not a code change. This release
makes the app honest about it instead of offering a button that cannot work.

## Reproduce

```sh
bun audit/bench.mjs --runs 15                 # this version

# The baseline worktree needs its own install; symlinking node_modules fails
# the build, because Turbopack rejects a symlink out of the filesystem root.
git worktree add /tmp/emu151 origin/feature/register-details-v1.5.1
cd /tmp/emu151 && bun install && bun audit/bench.mjs --runs 15

bun test lib electron
bun run verify

# The claim that matters most for this release: the build needs no network.
HTTP_PROXY=http://127.0.0.1:9 HTTPS_PROXY=http://127.0.0.1:9 \
  http_proxy=http://127.0.0.1:9 https_proxy=http://127.0.0.1:9 \
  bun run build
```
