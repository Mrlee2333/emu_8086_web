## vs v1.4.0

- **No performance regression.** Step throughput (~14.8 M steps/s) sits at the
  top of the v1.4.0 band (~12.5 M steps/s measured on the same machine);
  snapshot (~0.0067 vs ~0.011 ms) and print-loop (~8.5 vs ~8.4 ms) match, and
  `findNextMatch` (~0.24 vs ~0.4 ms) is within noise. No emulator-core file was
  touched — the diff is packaging config, the Electron main process, and one
  new pure helper.
- **Memory bounded, and strictly better than shipped.** v1.4.0 could spawn an
  unbounded chain of full app instances (each with its own Chromium helpers and
  server), which is how it froze machines. That path is closed: the child runs
  in Node mode and a single-instance lock caps the app at one instance. All
  v1.4.0 bounds are unchanged.
- **One new startup cost, small and bounded.** `asarUnpack` moves
  `.next/standalone` out of the asar. This does not change installed size
  (same bytes, different container) but does mean the DMG no longer compresses
  that tree as well inside the archive. The app also spends a few hundred ms
  verifying its own signature at launch — the same cost macOS already charged
  for the broken v1.4.0 bundle.

## Fix detail (for the next audit)

- v1.4.0's three launch defects were all in the packaging/launch path, none in
  shared code: an unsealed bundle (`CSC_IDENTITY_AUTO_DISCOVERY=false` skips
  signing entirely, so no `Contents/_CodeSignature` was written), the bundled
  server being unreachable (`.next/standalone` was inside `app.asar` while the
  resolver looked beside it and launches it with `spawn`), and the recursive
  spawn (a packaged Electron binary ignores a script argument and boots the
  app again — fixed with `ELECTRON_RUN_AS_NODE=1`).
- New guardrails so this class of bug cannot ship silently:
  `scripts/after-pack.mjs` seals any bundle that fails
  `codesign --verify --deep --strict`, and `release-desktop.yml` fails the
  release if the seal or the bundled server file is missing.
- Watch out next time: `ELECTRON_RUN_AS_NODE` is inherited by child processes.
  Any future `spawn` from the main process needs the same explicit env, and my
  own test harness hit exactly that trap while verifying this fix.
