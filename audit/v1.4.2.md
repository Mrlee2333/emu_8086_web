## vs v1.4.1

- **No emulator-core regression.** The step loop and `capture()` are within
  measurement noise (≤5 %, and the two directions disagree across runs, so
  this is JIT variance rather than a real delta). The 3000-line print loop
  retains the identical 2000 lines / 1999 chars. Nothing in the fetch-decode-
  execute path changed.
- **Two measured wins, both large enough to be unambiguous.**
  - Reading `machine.output` no longer re-joins the console line array.
    1000 reads went from 30.18 ms to 0.0075 ms. At the v1.4.1 rate the
    full-IDE render the loop triggered on every tick was allocating ~160 KB of
    joined string per frame for output that had not changed.
  - Memory search is 2.3x faster on the dense worst case. This one is worth
    flagging because the first implementation was *slower* than what it
    replaced: `searchAndCount` scanned the whole 64 KiB space unconditionally,
    while the old `findNextMatch` + `countMatches` pair stopped as soon as it
    had the 1000th match. Fixed by breaking out once both the next hit and
    the count cap are settled, and pinned by a test that counts byte reads
    through a `Proxy` (see "Fix detail").
- **Memory bounds strictly improved, and one unbounded path is now closed.**
  v1.4.1 retained up to 32 MiB of step-back snapshots and captured a full
  snapshot on every ~16 ms run tick, so that ceiling was reached in about
  eight seconds of running. Checkpoints are now rate-limited to one per 250 ms.
  More significantly, the shadow stacks behind the stack panels had no cap at
  all, and every snapshot copied both arrays — a program looping `push ax`
  could retain hundreds of megabytes across the history. `dataStack` is capped
  at 4096 (oldest dropped; `SP` and memory remain the source of truth) and
  `callStack` halts with an explicit "recursion too deep" error rather than
  discarding a return address that `ret`/`iret` would then read.
- **Run-loop throughput is now honest, and lower at the top end.** The speed
  control is labelled in milliseconds per instruction. v1.4.1 ran up to 200
  instructions per timer tick *regardless* of that setting, so the label
  described nothing. v1.4.2 retires what the elapsed time owes and renders at
  most once per frame, so the ceiling is ~1,000 instructions/s at the fastest
  setting where v1.4.1 could reach ~50,000/s. This is a deliberate correction,
  not a regression: a long program still finishes sooner because v1.4.1 spent
  most of that budget on renders. Watch this number next release — if real
  users want raw throughput back, raise `MAX_STEPS_PER_FRAME` rather than
  reintroducing a per-tick render.
- **One user-visible behavioural change in a hidden tab.** The loop is driven
  by `requestAnimationFrame`, which browsers do not call for a hidden
  document. A hidden tab therefore falls back to a timer and resyncs its
  accumulator on return, so a program never silently freezes while the toolbar
  still reads "running".
- **Bundle.** 743,962 B → 668,076 B raw, 216,464 B → 197,718 B gzipped, from
  moving `qrcode` behind a dynamic import (it is only needed by the Share
  dialog) and dropping a `localStorage` write that nothing ever read. A
  `bun run bundle:budget` gate now fails CI if `/` climbs back over 720 KB.

## Fix detail (for the next audit)

- **The dense-search regression is the one to remember.** `countMatches` was
  never actually O(memLength × matches) — `from` advanced monotonically, so it
  never rescanned. Its real cost was that the UI made *two* traversals (one to
  find, one to count), and its useful property was that it could stop early at
  the display cap. Any "single-pass" rewrite that scans the full space
  unconditionally is slower. `audit/bench.mjs --json` reports which search API
  it exercised so a report cannot silently compare two different searches.
- **`requestAnimationFrame` cannot be verified in a headless preview.** The
  automated browser used for review never fired it (0 callbacks in 1.3 s), so
  the run loop was exercised with a timer-backed shim. The rAF call itself is
  the one piece of this version that has not been confirmed against a real
  compositor. Worth one manual pass on a high-refresh display.
- **The share layer gained its first tests.** `lib/share/share.test.ts` covers
  code generation, the rate limiter, the IP trust boundary and the request
  guards. v1.4.1 had none, which is how the `X-Forwarded-For` trust survived
  several review rounds.
- **Supply-chain guardrails added, because none existed.** CI now runs
  `bun audit --audit-level=high` and the desktop release job installs with
  `--frozen-lockfile`. The release workflow's version interpolation was a
  script-injection sink in a job holding `contents: write` and
  `actions: write`; it now passes through `env` and is validated as semver.
- **Still unaddressed, deliberately.** `Machine` mutates its registers,
  flags, memory and console in place, so `React.memo` cannot bail out on the
  panel props and the whole IDE re-renders on every tick. The correct fix is
  `useSyncExternalStore` slices (or a `version` counter) per panel. This
  version only mitigated it at the leaves (memoized editor overlay and gutter
  rows). `experimental.reactCompiler` is the cheap experiment to try first.
  Until then, first-load size and per-tick render cost are coupled to the
  single 1,655-line `IdeWorkspace` component.
